## What was done

1. **Audit (read-only) of both hosts** → `docs/environment.md`. First pass found four blockers (pve key rejected, sudo needed a password, Docker absent, GPU held by big-cat). Phil fixed the first two, decided the third and fourth (see below).
2. **Proxmox (pve):** verified VMID 102 = `k8s-gpu-1` with `qm list`; `pvesm status` showed `local` (dir) and `local-zfs` (zfspool) on the same pool with 1.34 TiB free. Phil confirmed `local-zfs`. Ran `qm set 102 --scsi1 local-zfs:400,iothread=1` → `local-zfs:vm-102-disk-2`, hot-plugged as `/dev/sdb` (serial `drive-scsi1`) with no VM restart.
3. **VM (gpu):** confirmed `/dev/sdb` had no signatures, then GPT + one partition (`parted`), `mkfs.ext4 -L forge -m 0`, `/srv/forge` created, fstab line `UUID=a44b7035-… /srv/forge ext4 defaults,nofail 0 2`, `mount -a` OK. Created `/srv/forge/{models,db,profiles,jobs}` owned by `hqadmin`.
4. **Reboot** of the VM, then re-verified the mount and re-ran the GPU check. Both pass.
5. **Phase 0 item 3 (data root):** containerd's data root stays on the root disk at `/var/lib/containerd`. Forge will use bind mounts under `/srv/forge` in its `compose.yaml` (Phase 2); no runtime configuration change was needed or made.

## Decisions taken during Phase 0

- **No Docker CE.** The VM runs containerd 2.3.3 + nerdctl 2.3.5 + NVIDIA Container Toolkit 1.19.0 for other workloads; installing `containerd.io` risked breaking them. Forge uses `nerdctl compose` (rootful, via `hqadmin`'s passwordless sudo). `docs/requirements.md` v2 updated accordingly (included in this PR).
- **GPU sharing:** Forge expects the GPU to itself. Phil stops the `big-cat` voice stack before Forge sessions. `forge-api` (Phase 2) implements a free-VRAM guard: refuse to start `comfyui` if `nvidia-smi` free memory < `FORGE_MIN_FREE_VRAM_GB` (default 80), naming the processes holding VRAM. Forge never touches big-cat.
- **Kubernetes:** kubelet is running but its control plane (`k8s-cp-1`, VMID 103) is stopped, so it hosts no pods. Left as-is per §2. Whether to disable the unit is Phil's call.

## Surprises / worth knowing

- **Docker was never on this VM.** Requirements v1 assumed it; the audit is what caught it.
- **big-cat was holding 62.8 GB of VRAM** (vLLM at 0.6 GPU share + TTS) at the start of the session. After Phil stopped it and the VM rebooted, its three containers sit in `Created` state and its systemd unit `big-cat-stack.service` is enabled but `inactive (dead)` — its `WorkingDirectory=/home/youruser/big-cat/deploy` is a placeholder path, so it can't start at boot. Not Forge's problem, but Phil may want to know the stack does not auto-start after a reboot.
- **Host `nvidia-smi` reports "No devices were found" for the first seconds after boot** while the driver initialises; a container check a few seconds later succeeded. Anything Forge starts at boot must wait for the driver and for `/var/run/cdi/nvidia.yaml` (regenerated by `nvidia-cdi-refresh`).
- **Root disk is 76 % full** (69 G free). Model weights must go on `/srv/forge` from day one; Phase 1 image builds should also point their caches there where possible.
- **Proxmox snapshot:** VM 102 has a snapshot parent `phase-09c-openwebui-vllm-working`. The new `scsi1` disk is not part of it; rolling back to that snapshot would detach `/srv/forge` (the zvol itself would remain).
- **Caddy** is a single `/etc/caddy/Caddyfile` in LXC 106 (192.168.1.2), Cloudflare DNS ACME. Adding `forge.gattonehq.com` is one site block plus a DNS record; snippet is in environment.md for Phase 3.
- The workstation's `~/.ssh/config` is literally wrapped in a PowerShell here-string. ssh ignores the junk lines, but it should be cleaned up.
